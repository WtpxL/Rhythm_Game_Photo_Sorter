# 02 技术方案

版本：v1.0（2026-10-15）
状态：草案，随开发更新。

## 1. 技术选型

- 语言与运行时：Python 3.11+
- UI：PySide6（桌面窗口）
- OCR：RapidOCR（基于 ONNX Runtime）。默认中文模型 PP-OCRv4(ch) 处理常规文本；另加载日文识别模型
  japan_PP-OCRv4_rec（复用中文检测/方向分类，仅识别模型换日文）作为补充通道，用于彩色/描边艺术字日文标题。
  模型随程序打包（data/ocr_japan/），来源 RapidAI/RapidOCR 官方仓库；PaddleOCR 作为备选
- 图像处理：OpenCV（透视校正、ROI 定位、预处理）
- 存储：SQLite（曲库 + 图片索引）
- 曲库抓取：Playwright（无头浏览器，用于通过 wiki.arcaea.cn 的反爬验证）
- 打包：PyInstaller（Windows，one-folder 绿色版）
- 版本管理：Git

## 2. 系统架构

分层：

- 表现层 UI：主窗口、预览、校对弹窗、设置
- 业务层：导入、识别流水线、校对、整理、查询
- 数据层：SQLite、文件系统
- 外部：联网曲库抓取（本地缓存优先）

模块划分（代码目录草案）：

```
src/
  app/             # 入口与启动
  ui/              # PySide6 界面
  core/            # importer / pipeline / organizer / searcher
  recognizers/     # arcaea / maimai / chunithm，每游戏一个
  library/         # 曲库加载与匹配
  db/              # SQLite 访问
  network/         # 曲库抓取与解析
tests/
docs/
devlog/
```

## 3. 识别流水线

输入图 → 游戏分类 → 预处理（透视校正/裁剪/增强）→ ROI 定位 → OCR → 曲库模糊匹配 → 置信度判断 →（不确定）校对弹窗 → 入库。

各游戏使用独立配置描述歌名、难度的 ROI 与预处理参数，新增游戏时只加配置与识别器。

Arcaea 移动端截图按宽高比区分平板（~1.44，如 2360x1640）与手机横屏（~2.22，如 2400x1080）两种布局，
各自一套歌名/难度 ROI；歌名 ROI 下沿卡在歌名与曲师名之间，避免曲师名混入歌名文本。
舞萌/中二在歌名 ROI 之外，再以难度行 y 为锚收一条窄带（歌名紧贴难度名下方），排除其下的「新纪录/达成率」等面板行；
面板噪声过滤统一在 common.is_panel_label 处理（覆盖简/繁/日写法与含 % 的达成率文本）。
歌名匹配（matcher.similarity）除「前缀命中」外增加「近似前缀」：歌名被立绘遮挡只读到前半段、且截断处末字被 OCR 读错时（如 Lost Emc → Lost Emotion feat. nomico）仍按前缀命中给分，减少漏判。

## 4. 数据模型（草案）

表 images（图片索引）：

- id：主键
- source_path：原图绝对路径（唯一）
- organized_path：整理后路径（可空）
- game：游戏标识
- title：歌名原文
- title_aliases：中文别名（可空）
- difficulty：难度名称
- note：备注（自由文本，可空）
- status：confirmed / pending / skipped / deferred
- imported_at：导入时间

表 songs（曲库）：

- id、game、title、title_aliases、difficulty、source、updated_at

## 5. 联网策略

- 识别过程离线运行。
- 曲库刷新来源（阶段 0 已验证）：
  - Arcaea：wiki.arcaea.cn（MediaWiki API），经 Playwright 无头浏览器通过 Anubis 反爬验证后调用。
  - 舞萌/中二：萌娘百科「Maimai系列/曲目列表」「CHUNITHM/曲目列表」页面，经 Playwright 渲染后解析表格。
- 抓取失败/来源不可用：记录原因并反馈用户，不静默失败。
- 联网与安装依赖前请求用户授权。
